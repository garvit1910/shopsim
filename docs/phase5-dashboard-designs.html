Phase 5 · design review

Five ways to watch a synthetic market think

Each tab is a working, animated mock of the Phase-5 live experience: press play, watch DAY 1→14 advance, scrub, and click any shopper to open the inspector. All five run on one seeded mock market whose data is shaped exactly like the real endpoints (events.jsonl records, results_state series, worldview payloads) — so the design you pick ports to the real stack by swapping the mock API for the real one.

Decision made (2026-08-18): Terminal base + The Floor's live-market feel, no particle theater — built as ★ V2 · Trading Terminal (tab 1). Broadcast survives as a story-mode demo toggle inside it; the Living Graph returns as a deepened inspector feature (decision replay with real probabilities, version rails). D1–D5 remain for reference. Keyboard: 0–8 switch tabs, Esc closes the inspector, Space plays/pauses.

What is real here, and what is mock

Real: every layout is driven by data shapes the shipped engine already produces — per-tick event batches (with shopper ids, creatives, prices, need lifecycles), per-tick cumulative series (funnels, CTR, preference drift per concept×segment, reference price), and per-shopper worldview payloads (beliefs with confidence and provenance sentences, cause-stamped preference chains). Maya #0042's preference timeline uses the contract-tested golden-chain numbers verbatim: 0.45 → 0.476 → 0.532 → 0.614 → 0.714 → 0.761.

Mock: the market itself is a ~60-line seeded generator (no HydraDB, no LLMs, no engine), and shopper display names are cosmetic aliases for offsets. Counters are honest to a 200-shopper × 14-day run — about 2,000 impressions and a handful of buys — not inflated for effect. The real run at this scale advances one day every ~5–8 s; the mock plays one day every ~2.5 s at 1×.

Prerequisite check — the live UI is barely blocked at all

Phase 3/4 shipped more live surface than PLAN.md's Phase-5 text assumes. Below is what the frontend can read today, what needs a small additive endpoint, and the two items that need Atishay's ack.

1 · What the frontend can already read live

  • HTTP, shipped (runner/api.py, via python -m shopsim.runner serve): GET /runs (registry rows incl. status + run_index), GET /runs/{id}/progress (atomic per tick: tick, ticks, status, per-phase wall-clocks), GET /runs/{id}/results (404 until complete).
  • On disk every tick (not yet over HTTP): events.jsonl — fsync'd per tick, every funnel event with shopper id / subject / cause_creative / price, plus NEED lifecycle records and TICK_COMPLETE markers (free tick bucketing); results_state_{tick}.json — the full ResultsAccumulator every tick: funnel by segment, CTR by day, per-creative + per-page funnels, goal split, preference-drift series per concept×segment (a live PREFERS sweep already runs every tick), reference-price trajectory, motif stats.
  • HydraMem mid-run reads (Bolt, second process — the exact pattern already ships in export-fixtures): get_shopper_worldview (beliefs + confidence + provenance sentences), get_preference_history (cause-stamped chain incl. SEED), get_belief_history, get_trace (motif paths + scalars).

2 · What is post-run only

Final results.json (but its content is derivable mid-run: ResultsAccumulator.from_state().results(manifest) renders the full C3 shape from any tick's snapshot — verified that results() never touches the constructor-only params) and the cross-arm comparison.json written after all arms finish.

4 · Polling vs SSE — polling wins

Ticks land every ~5–8 s at demo scale (78.4 s measured for 200×14). 2 s polls of three small atomic files, with results-live fetched only when progress.tick advances. No SSE/WebSockets — nothing at this cadence justifies them for a hackathon.

5 · Is anything blocking Phase 5?

No. Two items need Atishay's ack at the next sync (his lane), then everything above is additive:

  • CONTRACT v3.5-draft: the endpoint set above added to runner/api.py (his file, read-only additions + the launch POST that spawns the engine — Law 8 intact: the dashboard still never writes the graph).
  • CONTRACT v3.5-draft: the ~15-line belief sweep in runner/results.py::end_tick_sweep (overlaps his Phase-6 belief_drift work — flagged, never merged silently).

Gotchas found (planned around, not blockers)

  • Preference before→after values are not in events.jsonl (supersessions are recomputed, never logged) — the live feed budgets ≤ 8 preference-history fetches/tick for featured shoppers.
  • results_state keeps only the last 2 ticks — results-live must glob-max and retry-lower on the deletion race; replay never needs old snapshots (final results carry every cumulative series).
  • run_config.json lives in runs/experiments/<label>/, not per-run dirs — /config resolves via the registry row's label.
  • Repeated demo runs degrade HydraDB write throughput as the store grows — keep the documented store-reset ritual before the video take.
